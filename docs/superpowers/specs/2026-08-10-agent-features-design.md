## 1. 背景与目标

### 1.1 背景

项目当前已完成阶段八主线（8.1 模型抽象层、8.2 用户可控模型选择、8.3 Auto 与全局默认），
具备 7 模型可切换、离线/API 两级选择、引用核验 + 六维可信评分闭环等能力。
阶段八的 8.4（任务编排式多智能体）与 8.5（工具调用式智能体）尚未实施。

本次改进的目标：
- 让项目在竞赛中具备架构级亮点与现场演示亮点；
- 提升专业场景（合同审查、时效查询、多法条交叉）的回答质量与专业度；
- 形成「可信智能体」答辩叙事——AI 可自主调用工具，但每一步都被核验。

### 1.2 已确认的约束（与使用者探讨确认）

| 约束项 | 结论 |
|---|---|
| 比赛时间 | 1 个月以上，可完整落地 8.4 + 务实版 8.5 |
| 工具集范围 | 稳健版：检索法条 + 查询法律时效 2 个工具（不做赔偿计算、不做合同条款解析） |
| 答辩侧重 | 均衡：功能实现 + 文档/演示支撑并重 |
| 方案 | 方案 A：8.4 完整落地 + 8.5 务实版（本设计） |

### 1.3 关键判断（设计依据）

- **准确性**：专用提示词 + 专用输出结构（合同风险清单）+ 按需多次检索（工具调用）
  对专业度和准确度是实打实的提升；但准确性最终仍由引用核验闭环兜底，
  工具调用只是让模型「看到更多」，不替代核验。
- **效率**：智能体链路比单次生成多 1~N 次模型调用，**单次回答延迟通常增加**；
  真正带来「毫秒级变快」的是缓存层（阶段二，另立实施项，不在本设计范围）。
  智能体带来的是「不浪费」：时效问题走直查路径、合同问题走专用管线。
  答辩承诺口径：更准、更专业、更可信，**不承诺更快**。
- **比赛亮点**：多模型切换已是「换引擎」级能力；「主管-专家分派 + 工具调用轨迹」
  是架构级亮点，且与现有可信闭环合成独特叙事：「可信智能体」。

## 2. 现状分析（改造起点）

| 模块 | 现状 | 与本设计的关系 |
|---|---|---|
| `src/pipeline/intent_router.py` | 3 类意图：legal_qa / greeting / general_non_legal | 保留不动，调度器在其之上扩展任务类型 |
| `src/pipeline/answer_pipeline.py` | 统一流水线：重写 → RAG → 生成 → 核验 → 评分；含重生成与文档分析模式 | 核心复用；合同/时效管线在旁路复用其内部能力 |
| `src/llm/qwen_model.py` + `api_client.py` + `base.py` | 文本进文本出，多模型注册表路由 | 新增 `generate_with_tools()` 契约（函数调用） |
| `src/knowledge_base/law_validity.py` | 注册表时效服务，仅在引用核验警告中使用 | 时效查询管线的直查引擎；工具 check_law_validity 的执行者 |
| `src/knowledge_base/vector_store.py` | 向量检索 + 相关度阈值 + 去重 | search_articles 工具的执行者 |
| `web/backend/main.py` | SSE 流式（meta/token/done）+ WS 异步核验 | 新增 agent_status 事件类型（向后兼容） |
| 前端（Vue） | 消息渲染、详情面板、状态标签 | 新增 agent_status 处理 + 工具轨迹区块 |
| 任务注册表 / verification_worker | 异步核验闭环 | 不变，最终回答照常核验；轨迹随 meta/done 传递 |

**三条不可破原则**：
1. **回退安全**：任务分类置信度不足一律落回法律问答管线（最坏情况 = 现状，不退化）。
2. **可信闭环不放松**：无论哪条管线、模型是否调用工具，法律类最终回答照常过
   引用核验 + 六维评分。
3. **用户可控不变**：智能体不做模型自动路由，用哪个模型仍由用户决定。

## 3. 总体架构

新增智能体层，集中放在新目录 `src/agents/`（四个文件，职责单一）：

```
输入守卫 → 任务调度器（3 类任务 + 寒暄/通用直通）→ 主管分派 ↓
  ├── 法律问答 ────→ 现有流水线不变（新增可选工具调用，模型自主决定）
  ├── 合同审查 ────→ 文档优先 → 专用提示词 → 结构化风险清单 → 核验（含文档引文）
  ├── 时效查询 ────→ 直查注册表 → 确定性结论 → 模型润色 → 来源标注
  └── 寒暄/通用 ────→ 现状完全不变
      所有法律类管线出口 → 引用核验 + 六维评分闭环（时效查询除外：确定性数据，不核验）
```

| 新文件 | 职责 | 类比 |
|---|---|---|
| `src/agents/task_scheduler.py` | 判断任务类型并分派 | 前台接待员 |
| `src/agents/tools.py` | 两个工具的说明书 + 执行者 | 员工手里的工具包 |
| `src/agents/agent_loop.py` | 工具调用循环引擎（上限 3 轮） | 员工的工作流程 |
| `src/agents/trace.py` | 工具调用轨迹数据模型 | 工作留痕记录 |

接入点：`answer_pipeline.py` 的 `run` / `prepare_context` 在 `classify_intent` 之后
调用调度器；SSE 生成器根据任务类型选择管线；`main.py` 的流式端点新增
`agent_status` 事件类型。

## 4. 任务调度器（8.4 落地）

### 4.1 任务类型与触发规则

确定性规则分类（不用大模型判断：快、稳、便宜、可解释），全部不命中落回 `legal_qa`：

| 任务类型 | 触发信号 | 兜底 |
|---|---|---|
| `legal_qa` | 默认 | — |
| `contract_review` | 提问含审查/风险/条款/看合同类词 **且** 携带上传文档 | 有审查意图但无文档 → 礼貌引导「请上传合同文件」+ 简述可审查维度；有文档但提问为普通法律问题 → 照旧 legal_qa（文档注入） |
| `validity_check` | 提问含注册表废止法律名（婚姻法/合同法/担保法…，从 law_registry.json 取）**且** 含有效/废止/还有效/生效/失效类词 | 命中不全 → legal_qa |

分类规则封装为独立函数，配 pytest 单测（新增测试用例，延续现有 tests/ 风格）。

### 4.2 三条管线设计

**① 法律问答管线**：与现状完全一致。唯一变化：管线向模型开放工具
（见第 5 节），模型认为「一次检索不够」才调用；不调用时行为与今天完全一致（零回归）。

**② 合同审查管线**（重点新能力）：
- 专用系统提示词，输出**结构化风险清单**（Markdown，现有渲染器即可）：
  ```
  【合同风险清单】
  1. ⚠️ 条款类型：试用期约定
     风险点：约定试用期 6 个月，超出法定上限
     法律依据：《劳动合同法》第十九条（首次约定不得超过 6 个月）
     修改建议：改为不超过 6 个月…
  【总体评价】
  ```
- 检索策略不变（RAG 照常注入合同相关法条）。
- **核验升级——文档引文核验**：`CitationVerifier.verify()` 新增可选
  `user_documents` 参数，回答中引用文档原文的句子与上传文档逐字比对，
  防止模型编造合同条款。这是「核验侧重文档内条款与引用法条一致性」的落地。
- 输出结构不同的提示词模板：`src/llm/qwen_model.py` 的 `get_system_prompt`
  按任务类型返回（扩展 `get_system_prompt` 的 intent 参数取值）。

**③ 时效查询管线**（快路径）：
- 直查 `law_registry.json`，结论核心事实（废止日期、替代法律）完全由注册表给出，
  提示词约束模型不得编造时效事实。
- 一次轻量生成：模型组织语言 + 补充实务提示（如「婚姻法废止后，相关事项按
  民法典婚姻家庭编处理」）。不检索、不核验、不评分，回答标注
  「来源：法律时效注册表」。
- 答辩点：「此问题零 RAG 零核验，直查注册表秒级出结论——智能体选最优路径，
  而非什么都硬调大模型」。

## 5. 工具调用引擎（8.5 落地）

### 5.1 工具定义（`src/agents/tools.py`）

| 工具名 | 给模型看的说明（参数） | 执行者（真实代码） |
|---|---|---|
| `search_articles` | `query`（检索词，必填）、`law_name`（可选指定法律） | 向量库检索：按 `Config.RETRIEVAL_MIN_RELEVANCE` 过滤 + `article_key` 去重，返回 Top-K 法条（复用现有检索逻辑与阈值） |
| `check_law_validity` | `law_name`（法律名称） | `LawValidityService` 查注册表，返回 {是否有效, 状态, 废止日期, 替代法律, 提示语} |

工具执行只触碰本地向量库与本地注册表，无任何外部调用。

### 5.2 循环引擎（`src/agents/agent_loop.py`）

```
第 1 轮：模型拿到问题（含首轮 RAG 结果）→ 自主判断
  ├─ 不需要工具 → 直接生成最终回答（与今天完全一致，零成本零回归）
  └─ 需要工具 → 输出调用指令 → 代码在本地执行
     第 2 轮：模型看到工具返回 → 再判断（上限 3 轮）
        └─ 输出最终回答 → 流式输出
```

- **轮次上限**：`Config.AGENT_MAX_TOOL_ROUNDS = 3`；每轮工具决策 token 上限约 512。
- **出错降级**：工具循环任何一步异常 → 自动退回普通生成路径（等于现状），
  绝不返回空白或半截回答。
- **结果约束**：工具结果只作模型参考，不直接进入回答；最终回答的引用仍以
  引用核验为准，工具结果不作为免检证据。

### 5.3 模型层改动（顺阶段八架构，最小侵入）

- `src/llm/base.py`：`BaseLLMModel` 新增 `generate_with_tools()` 契约。
- `src/llm/api_client.py`：新增 `complete_with_tools()`（OpenAI 兼容 function
  calling，百炼全系支持）。
- `src/llm/qwen_model.py`：`QwenModel` 实现 `generate_with_tools()`（仅 API 路径）。
  本地 7B 一律抛 NotImplementedError，`agent_loop` 捕获后自动退回普通生成——
  即「提示词注入」降级（告诉模型「检索结果已由 RAG 提供，直接作答」，等于现状）。
- 本地引擎不开启工具模式：7B 工具调用能力弱，降级为提示词注入（与指南一致），
  前端无感知变化。

### 5.4 SSE 事件流（解决「工具循环 vs 流式」矛盾）

```
event: meta           {task_type:"legal_qa", agent:true}
event: agent_status   {step:1, tool:"search_articles", status:"running", detail:"正在检索《工伤保险条例》…"}
event: agent_status   {step:1, tool:"search_articles", status:"done",   result:"命中 5 条相关法条"}
event: token          {text:"根据《工伤保险条例》…"}      ← 最终回答照常逐字流式
event: done           {tool_trace:[…], trust:…}
```

`agent_status` 为新增事件类型，向后兼容（旧前端忽略未知事件）；
非流式 `/api/chat` 路径：工具循环同步执行，轨迹随响应返回。

### 5.5 轨迹数据模型（`src/agents/trace.py`）

每步记录：`{step, tool_name, arguments, result_summary, success, cost_ms}`。
随 `done` 事件返回并存入任务注册表，供详情面板展示与统计。

## 7. 核验闭环与安全

| 管线 | 核验与评分 | 说明 |
|---|---|---|
| 法律问答 | 引用核验 + 六维评分 | 与现状一致 |
| 合同审查 | 引用核验（含文档引文核验）+ 六维评分 | 引用的法条照常核验；文档原文引用逐字比对 |
| 时效查询 | 不核验不评分 | 确定性数据，标注来源，轻量路径 |
| 工具调用结果 | 只作模型参考，不直接进入回答 | 最终回答引用以核验为准 |

安全清单：
- 输入守卫最先跑：滥用拦截、PII 脱敏发生在调度之前。
- 工具只在本地执行：向量库 + 注册表，零外部调用。
- 循环硬上限：3 轮 + 每轮 token 上限，防死循环、防费用爆炸。
- 出错降级：工具循环异常自动退回普通生成，绝不空白。
- 工具参数清洗：长度上限、控制字符剔除。

## 9. 实施顺序与验收标准

| 步骤 | 内容 | 验收标准 |
|---|---|---|
| 1 | 任务调度器 + 三条管线（合同提示词 / 时效混合路径 / 文档引文核验） | 三类问题各输出正确结构；「审合同」无文档时有礼貌引导；pytest 回归全过 |
| 2 | 工具引擎（tools + agent_loop + generate_with_tools + SSE agent_status） | 多法条问题出现工具轨迹；普通问题零工具调用且回答与现状一致（零回归）；循环出错自动降级 |
| 3 | 前端（agent_status 处理 + 详情面板轨迹区块） | 状态提示实时显示；轨迹可展开；合同清单正常渲染 |
| 4 | 评测 + 架构文档 + 演示脚本 | 对比报告产出；流程图与 Q&A 就绪；演示脚本跑通 |
| 5 | 收尾：修改日志、CLAUDE.md 进度表、指南 8.4/8.5 更新 | 三份文档同步完成 |

预计总工作量：8~11 天。

主要风险与对策：

| 风险 | 对策 |
|---|---|
| 函数调用在个别模型不稳 | 出错自动降级重试，绝不返回空白 |
| 模型过度调用工具 | 系统提示词约束 + 3 轮上限 + 每轮 token 上限 |
| 合同文档过长 | 复用现有截断机制（`DOC_MAX_CONTEXT_CHARS`） |
| 注册表缺某部法律 | 时效查询兜底落回法律问答管线 |
| 任务分类误判 | 确定性规则 + 一律可回退 legal_qa，最坏等于现状 |

## 10. 明确不做（范围外）

- 赔偿/补偿金额计算工具、合同条款解析工具（指南原案 4 工具中的 2 个）——可核验性弱，留待二期。
- 复杂推理单设管线——工具调用已覆盖其场景（模型自主决定是否多次检索）。
- 缓存层（阶段二）——「更快」的杠杆，另立实施项。
- 模型自动路由——与「用户可控」原则冲突，明确不做。
- 知识图谱、微调（阶段七可选）——不在本设计范围。
