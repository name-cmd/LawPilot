================================================================================
阶段一  流式输出优化 —— 让对话体验像 ChatGPT 一样
================================================================================

【目标】优化现有流式输出体验，确保逐字显示稳定可靠、错误处理完善。

【预计耗时】2-3 天

【价值】大幅提升用户体验，竞赛演示时视觉效果更好，降低"感知等待时间"。

【说明】项目已经实现了 SSE 流式 + WebSocket 异步核验的基础框架
       （见 web/backend/main.py 的 /api/chat/stream 端点与
       web/backend/verification_worker.py），前端也已迁移至 Vue 工程
       （web/frontend/src）。本阶段的重点是稳定性加固和体验打磨，
       而非从零实现。

--------------------------------------------------------------------------------
1.1  当前流式实现的已知问题
--------------------------------------------------------------------------------

  问题1：流式失败时降级逻辑不完善
    现状：前端流式请求失败后仅打印错误日志，用户看到的是空白回答。
    改进：为前端问答交互模块（Vue 组合式函数 useChatStream，旧版为
          index.html）增加异常捕获与自动降级：流式不可用时自动转调
          同步问答接口，以一次性渲染的方式给出回答，并用提示条告知
          用户"已切换至同步模式"。

  问题2：LLM 推理中断后 SSE 连接不释放
    现状：后端流式生成器抛异常后，事件流被中断，但任务注册表中
          的状态可能残留，前端连接也可能未正确关闭。
    改进：在流式响应生成器中增加统一的收尾处理，无论成功、异常还是
          客户端主动断开（例如关闭浏览器标签页），都执行资源释放与
          任务状态登记（完成 / 异常 / 已断开），保证无泄漏、无残留。

  问题3：前端"正在输入…"动画不够流畅
    现状：简单的文字闪烁，视觉体验一般。
    改进：实现类似 ChatGPT 的打字光标动画；用帧调度批量刷新页面内容
          避免逐字重绘导致的卡顿；流式过程中显示"生成中"状态标签，
          回答完成后、异步核验进行中显示"核验中"标签，核验结束自动消失。

--------------------------------------------------------------------------------
1.2  加固步骤一：前端错误处理与降级重试
--------------------------------------------------------------------------------

  修改对象：前端问答交互模块（web/frontend/src/composables/useChatStream.ts）。

  具体做法：
  - 将"发送问题并消费流式响应"封装为一个统一函数，内部创建请求
    中止控制器，设置 3 秒超时判定：3 秒内未收到响应头即认为流式不可用。
  - 正常路径：按原有逻辑逐段消费 SSE 事件流（meta → token → done），
    边接收边渲染。
  - 降级路径：捕获到任何流式异常（超时 / 网络错误 / 非 2xx 状态码）时，
    自动改调同步问答接口，将完整回答一次性渲染，并在界面弹出提示
    "已切换至同步模式（流式暂不可用）"。
  - 兜底路径：同步接口也失败时，给出明确的错误提示，提示用户检查服务
    是否正常运行，而不是静默失败。

  达到的效果：任何网络或后端异常下，用户都不会再看到空白回答，演示
  时不会因偶发抖动中断体验。

--------------------------------------------------------------------------------
1.3  加固步骤二：后端流式资源释放
--------------------------------------------------------------------------------

  修改对象：web/backend/main.py 的流式问答端点、web/backend/task_registry.py。

  具体做法：
  - 在流式响应生成器中补充三类收尾分支：客户端断开（正常情况，静默
    处理不报错）、内部异常（先向客户端推送 error 事件再结束）、正常
    完成；三者最终都统一进入"任务收尾"逻辑。
  - 任务收尾逻辑负责：把该消息在任务注册表中的状态标记为终态
    （完成 / 异常 / 已断开），并清理与该连接相关的资源引用。
  - 可选：为流式端点增加请求级别的连接关闭钩子，客户端断开时由
    FastAPI 侧主动中止生成器，配合上面的终态标记，彻底避免泄漏。

  达到的效果：前端关闭页面或网络抖动中断时，服务端无生成器残留、
  无任务状态卡死，长时间运行后内存与任务表保持干净。

--------------------------------------------------------------------------------
1.4  加固步骤三：前端体验打磨
--------------------------------------------------------------------------------

  修改对象：前端消息列表渲染组件（ChatMessage / AnswerContent）。

  具体做法：
  - 打字光标：回答流式输出期间在文本末尾显示一个闪烁的光标块
    （CSS 关键帧动画，约 0.8 秒一个周期），输出完成后自动消失。
  - 批量渲染：把流式收到的文本先放进缓冲区，用浏览器帧回调统一
    追加到页面，避免每个 token 都触发一次重绘；每批渲染后自动滚动
    到底部，保证用户始终看到最新内容。
  - 状态指示：生成中在回答上方显示"生成中"小标签；流式完成后、
    异步核验尚未结束时显示"核验中"标签；核验结果经 WebSocket 推送
    回来后标签消失，可信分角标同步更新。
  - 非流式路径保持原样：安全拦截、寒暄回复等同步响应不走打字机效果。

--------------------------------------------------------------------------------
1.5  验收标准
--------------------------------------------------------------------------------

  □ 提问后回答逐字出现（打字机效果），不是一次性显示
  □ 流式失败时自动降级到同步模式，有提示条告知用户
  □ 关闭浏览器标签页后 SSE 连接正确释放，服务端无泄漏、任务表无残留
  □ "生成中 / 核验中"状态标识显示正常，核验完成后自动消失
  □ 安全拦截、寒暄回复不走流式（保持原有同步响应）

================================================================================
阶段二  问答缓存层 —— 避免重复计算，大幅降低延迟
================================================================================

【目标】为法律问答流水线引入多层缓存机制，对相同/相似问题直接返回
        缓存结果，避免每次都执行完整的"检索→生成→核验→评分"流水线。

【预计耗时】2-3 天

【价值】
  - 相同问题再次提问：从 15-60 秒 → 毫秒级返回
  - 相似问题：语义匹配命中后可跳过大模型生成
  - 减少不必要的模型推理，节省 GPU 与 API 成本
  - 竞赛答辩时可展示"缓存命中率"等性能数据

【现状分析】
  当前项目没有任何缓存机制：
    - 每次提问都会重新执行完整流水线
    - 相同问题连续问两次，两次都走检索+生成+核验
    - 查询向量每次重新计算，不缓存
    - 前端会话切换时翻看历史消息不会触发请求（该场景暂无重复计算）

--------------------------------------------------------------------------------
2.1  缓存架构总览
--------------------------------------------------------------------------------

  推荐三层缓存金字塔，自顶向下逐层命中：

  L1 精确问题缓存（内存）
    命中条件：问题文本与配置参数完全相同
    命中率预估约 5%，命中延迟 < 1 毫秒，直接返回历史答案

  L2 语义相似缓存（内存 + 向量）
    命中条件：问题语义与历史问题相似度超过阈值
    命中率预估约 15%，命中延迟 < 50 毫秒，复用相似问题的答案

  L3 嵌入向量缓存（内存）
    命中条件：同一查询文本重复计算向量
    命中率预估约 60%，省去重复的嵌入计算，服务于 L2 与 RAG 检索

  三层全部未命中时，才走完整流水线（15-60 秒）。

--------------------------------------------------------------------------------
2.2  L1 精确缓存：相同问题直接返回
--------------------------------------------------------------------------------

  新建文件：src/cache/exact_cache.py（精确查询缓存模块）。

  实现逻辑：
  - 用内存有序字典实现容量受限（建议 200 条）的缓存，插入时记录
    时间戳，读取时校验有效期（建议 30 分钟），超过即视为失效并清除；
    容量满时淘汰最久未使用的条目（LRU 策略）。
  - 缓存键由"问题文本（去掉首尾空白并转小写）＋ 是否启用 RAG ＋
    是否启用自一致性评估"拼接后取哈希生成，保证不同配置下的结果
    互不串用。
  - 提供三个基本操作：查询（命中返回结果并刷新新鲜度）、写入、
    清空；命中率统计由统一管理器负责。

  接入方式：
  - 在问答接口入口处先查缓存，命中则直接返回并在响应中标记
    "缓存命中"；未命中则走原有流水线，完成后写入缓存。

  注意事项（三条边界）：
  - 安全拦截类结果不缓存：滥用问题每次都必须重新过输入守卫；
  - 流式接口不做精确缓存：流式的价值就是即时反馈；
  - 含文档上传的请求不缓存：文档内容每次可能不同。

--------------------------------------------------------------------------------
2.3  L2 语义相似缓存：相似问题复用结果
--------------------------------------------------------------------------------

  新建文件：src/cache/semantic_cache.py（语义相似缓存模块）。

  实现逻辑：
  - 复用现有 bge 嵌入模型计算用户问题的向量，与缓存中历史问题的
    向量逐一做余弦相似度比较，取最高分。
  - 相似度超过阈值（建议从 0.92 起步，按实际效果调整）即命中，
    返回对应历史答案；未命中则把新问题向量与答案写入缓存。
  - 与 L1 相同：设容量上限（建议 500 条）与有效期（建议 1 小时），
    超限淘汰最旧条目。

  注意事项：
  - L2 引入了额外的向量计算开销（每次提问多一次嵌入），但远小于
    大模型推理；配合 L3 缓存后，这部分开销也可消除。
  - 仅对启用 RAG 的法律类问题做语义缓存，寒暄/通用类不做。

--------------------------------------------------------------------------------
2.4  L3 嵌入向量缓存：避免重复计算查询向量
--------------------------------------------------------------------------------

  修改对象：src/knowledge_base/embedder.py（嵌入模型封装）。

  实现逻辑：
  - 在查询嵌入方法上增加进程内 LRU 缓存（容量约 1000 条），对相同
    查询文本直接返回已算好的向量，不再重复调用嵌入模型。
  - 容量约占用几 MB 内存（1000 条 × 768 维 × 4 字节），可接受。

  达到的效果：高频问题（尤其配合缓存层使用时）的嵌入计算趋近于零。

--------------------------------------------------------------------------------
2.5  统一缓存管理器
--------------------------------------------------------------------------------

  新建文件：src/cache/manager.py（缓存统一管理器）。

  实现逻辑：
  - 对外只暴露两个操作：查询与写入，内部按 L1 → L2 顺序逐层尝试；
    记录总命中数、总未命中数，并提供命中率与统计明细的只读属性。
  - 写入时自动跳过安全拦截结果。
  - 在服务启动阶段完成管理器初始化（依赖嵌入模型实例），并新增一个
    缓存统计接口（/api/cache/stats），返回是否启用、命中数、未命中数、
    命中率，供前端展示或调试。

  达到的效果：三层缓存对流水线透明，后续新增缓存维度只需在管理器
  内扩展。

--------------------------------------------------------------------------------
2.6  前端缓存命中提示
--------------------------------------------------------------------------------

  修改对象：前端消息渲染组件。

  实现逻辑：
  - 检测到响应中带"缓存命中"标记时，在回答气泡旁追加一个绿色小徽章
    "⚡ 缓存命中"，鼠标悬停显示命中层级说明（相同问题精确匹配 /
    语义相似问题匹配）。
  - 徽章样式使用浅绿底、绿字的小号标签，与可信分徽章互不干扰。

--------------------------------------------------------------------------------
2.7  验收标准
--------------------------------------------------------------------------------

  □ 同一问题（如"劳动合同解除需要提前多少天通知？"）连续提问两次：
    第二次毫秒级返回，且气泡旁显示"⚡ 缓存命中"
  □ 访问 /api/cache/stats 能看到命中数 / 未命中数 / 命中率
  □ 语义相似问题（如"解除劳动合同要提前多久通知？"）能命中 L2 缓存
  □ 安全拦截类问题不被缓存（每次都会重新执行输入守卫）
  □ 缓存数据不会无限增长（LRU 自动淘汰最旧条目）

================================================================================
阶段三  服务端会话管理 —— 从 localStorage 到安全可控的 Session
================================================================================

【目标】将会话数据从前端 localStorage 迁移到服务端，实现安全的 Session
        管理、Token 过期机制和跨设备的会话持久化能力。

【预计耗时】2-3 天

【价值】
  - 安全性提升：Token 设有效期，超时自动失效
  - 数据不丢失：换设备/清浏览器后数据仍在（登录后从服务端恢复）
  - 多端同步：同一账号在不同设备上看到相同的会话历史
  - 为后期多用户部署打基础

【现状分析】
  当前的安全问题：
    1. 登录 Token 存在内存字典中，服务重启即丢失
    2. 前端所有数据存在 localStorage（会话、收藏、反馈、个人资料），
       换设备/清缓存后全部丢失，且任何能物理接触浏览器的人或 XSS
       脚本都能读取
    3. Token 永不过期
    4. 问答接口不校验 Token（测试阶段设计，生产不可用）

--------------------------------------------------------------------------------
3.1  最小实现方案：JSON 文件持久化 + TTL
--------------------------------------------------------------------------------

  说明：考虑比赛阶段不需要引入数据库，使用 JSON 文件作为轻量级持久化
  方案，避免 SQLite/Redis 的依赖复杂度。

  新建文件：web/backend/session_manager.py（服务端会话管理器）。

  数据结构：每个用户一条 JSON 文件（sessions/ 目录下按用户名命名），
  内容包含：用户名、显示名、头像、简介、会话列表、收藏列表、反馈列表。

  实现逻辑：
  - Token 管理：用安全随机字符串生成 Token（建议 32 字节以上），记录
    所属用户与过期时间（建议 24 小时）；每次校验通过自动续期；同一
    用户重新登录会吊销旧 Token（单点登录）；Token 表本身也持久化为
    JSON 文件，服务重启后恢复，启动时自动清理已过期的 Token。
  - 用户数据读写：提供资料（读取/更新）、会话（读取/保存）、收藏
    （读取/保存）等接口，全部落盘到对应用户的 JSON 文件；内存中做
    一层按用户名缓存，减少磁盘读写。
  - 容错：JSON 损坏时回退为空数据，不阻塞服务启动。

--------------------------------------------------------------------------------
3.2  改造后端的认证与会话接口
--------------------------------------------------------------------------------

  修改对象：web/backend/main.py。

  具体做法：
  - 用会话管理器替换原来的内存 Token 字典：登录时生成 Token 并持久化，
    校验接口改为查会话管理器（返回是否有效、用户名、显示名），登出
    时吊销 Token。
  - 新增四组服务端读写接口：会话列表读取/保存、收藏列表读取/保存、
    个人资料读取/更新；接口均以 Token 鉴权，Token 无效返回 401。
  - 测试阶段固定账号（root/123456）保持不变。

  达到的效果：数据真正落在服务端，换设备登录即可恢复。

--------------------------------------------------------------------------------
3.3  前端改造：双写策略（localStorage + 服务端同步）
--------------------------------------------------------------------------------

  修改对象：前端数据层（stores/sessions.ts、stores/favorites.ts、
  stores/auth.ts，旧版为 index.html）。

  策略：现有 localStorage 读写保持不变（向后兼容、离线可用），
  同时增加服务端同步。

  具体做法：
  - 保存时双写：本地立即写入（不阻塞界面），同时异步提交到服务端；
    服务端提交失败只告警、不影响本地使用。
  - 加载时优先服务端：登录后先从服务端拉取会话与收藏，成功则回写
    localStorage；服务端拉取失败或数据为空时降级读取本地数据。
  - 个人资料同理：显示名/头像/简介登录后从服务端恢复。

  达到的效果：换浏览器、清缓存后，同一账号的会话与收藏自动恢复；
  服务端不可用时仍可用本地数据继续使用（降级不中断）。

--------------------------------------------------------------------------------
3.4  为问答接口添加 Token 校验（可选渐进式启用）
--------------------------------------------------------------------------------

  修改对象：src/config.py、web/backend/main.py。

  具体做法：
  - 新增一个可配置开关"问答接口强制鉴权"，默认关闭（向后兼容，
    避免登录流程问题影响演示）。
  - 开关打开后，问答接口与流式接口在输入守卫检查之后校验 Token，
    无效则返回 401。
  - 答辩 PPT 中说明"已预留强制鉴权能力"，演示时保持关闭。

--------------------------------------------------------------------------------
3.5  验收标准
--------------------------------------------------------------------------------

  □ 登录成功后，sessions/ 目录下生成对应用户的 JSON 文件与 Token 表
  □ 服务重启后 Token 仍然有效（从文件恢复）
  □ Token 过期（默认 24 小时）后自动失效，前端跳回登录页
  □ 创建会话、收藏问答后刷新页面，数据仍然存在
  □ 换一个浏览器登录同一账号，会话和收藏自动同步
  □ 即使服务端接口不可用，localStorage 降级仍然可用

6.1  请求排队与限流

================================================================================
阶段八  模型层与智能体架构升级 —— 多引擎、用户可控、真多智能体 ★重构
================================================================================

【目标】将当前"全局开关切换本地/API"的单一模型层，升级为"多引擎、
        用户可控、带隐私模式、带真多智能体编排"的完整架构。

【预计耗时】主线 4-5 天 + 编排 3-4 天 + 工具调用 4-5 天（可选）

【为什么重构（相对 v2.0 的调整说明）】
  原方案"简单问题走本地 7B、复杂问题走云端 API"存在两个问题：
  1. 隐私逻辑颠倒——真正敏感的法律咨询（劳动争议、离婚财产、含身份证
     号的维权问题）往往恰恰是复杂问题，按原方案会被送往云端，隐私
     诉求反而被破坏；
  2. 多模型不等于多智能体——多模型只是"换引擎"，真正的智能体应具备
     自主编排与工具调用的能力。
  因此本阶段改为：模型选择权完全交给用户（离线/API、选哪个模型，
  Auto 仅跟随全局默认，不做自动路由）；同时引入任务编排与工具调用
  两层智能体能力。

【总体架构（文字描述）】
  完整请求链路自上而下为：
  前端（模型选择器：离线调用 / API 调用，API 下选具体模型）
    → 输入守卫（滥用拦截、PII 脱敏、隐私确认）
    → 任务路由（识别任务类型：法律问答 / 合同审查 / 时效查询；
      复杂推理由工具调用覆盖，不单设管线）
    → 任务编排层（主管按任务类型分派到对应的专业处理管线）
    → 模型层（严格按用户选择，路由到离线引擎或 API 引擎的某一模型）
    → 生成回答
    → 通用闭环（引用核验 + 六维可信评分，所有模型一视同仁）
    → 统计（模型使用 / 成本 / 工具调用记录）

  不变原则：无论使用哪个引擎、哪个模型，生成结果都必须经过引用核验
  与六维可信评分闭环——"可信"这一核心价值与"用哪个模型"完全解耦。

--------------------------------------------------------------------------------
8.1  模型抽象层与多引擎接入
--------------------------------------------------------------------------------

  现状：本地 Qwen2.5-7B 推理与百炼 API 客户端已存在（src/llm/qwen_model.py、
  src/llm/api_client.py），但 API 客户端绑定单一模型，切换模型靠全局开关。

  具体做法：
  - 定义统一模型接口（抽象基类，src/llm/base.py）：规定四个统一契约——
    同步生成、流式生成、模型名称、能力标签（是否本地、是否支持流式、
    上下文长度、价格档位、能力说明）。
  - 现有本地 Qwen 模型与 API 客户端都实现该接口，保持向后兼容。
  - API 客户端升级为"多模型注册表"驱动：用一份模型配置表登记每家
    供应商的信息——接口地址、密钥来源、模型名列表、价格档位、能力
    说明。预置：百炼千问三档（qwen-turbo 性价比、qwen-plus 均衡、
    qwen-max 高质量）与 DeepSeek 一档（deepseek-chat，低成本）。
  - 前端模型选择器（离线/API 两级）由该配置表动态生成，自动附带
    价格与能力说明。

  达到的效果：新增一个模型 = 在配置表里加一行，前端选择器自动出现
  新选项；答辩可现场演示"一键切换四个模型对比回答"。

--------------------------------------------------------------------------------
8.2  用户可控的模型选择（本阶段核心设计）
--------------------------------------------------------------------------------

  选择器 UI（前端交互设计）：
  - 模型选择器位于发送框旁，顶层为两个单选大选项：
    「离线调用」与「API 调用」。
  - 指针悬停在「离线调用」上时，显示文字提示气泡，如实说明本地模型
    的能力边界，例如："模型为 Qwen2.5-7B，参数量较小，效果不及 API
    调用模型，推荐处理隐私数据时使用"，让用户在知情前提下选择。
  - 选中「API 调用」后展开二级模型列表：Auto（跟随全局默认）与
    qwen-turbo / qwen-plus / qwen-max / deepseek-chat 四个具体模型，
    每个模型附带价格档位与能力说明（由 8.1 的模型配置表驱动生成）。
  - 选择粒度与记忆：设置页可配置全局默认模型（Auto 跟随它），选择器
    的选择对该会话生效、可随时修改；同一会话内的后续提问沿用当前
    选择。

  离线引擎（隐私模式）的就绪检测与展示：
  - 服务启动时自动检测 GPU 是否可用、本地模型文件是否就绪；两者都
    满足时才允许选择「离线调用」，否则该选项置灰不可选，悬停提示
    "当前环境未配置本地模型（需 GPU 与模型文件）"——选项始终可见，
    保证答辩时能展示系统支持双引擎，只是演示环境未开启。
  - 用户选择「离线调用」后，该会话的所有请求只走本地推理，问题文本
    与上传文档均不出本机、不调用任何外部 API。
  - 与输入守卫联动：系统检测到问题含身份证号、银行卡号等敏感信息时，
    在隐私确认弹窗中附加提示"该问题含敏感信息，建议切换离线调用
    处理"。

  设计说明：不做"按复杂度自动分配离线/API"，隐私决策应由用户做出；
  系统也不做任何按问题难度/类型的自动路由，选哪个模型完全由用户
  决定，Auto 只是"跟随用户自己设置的全局默认"。

  达到的效果：隐私叙事从"数据不出服务器"升级为"用户可选择的真正
  不出本机"；同时无 GPU 环境完全不受影响（纯 API 主流程不变），
  所有模型选择交互对用户透明、可解释。

--------------------------------------------------------------------------------
8.3  默认模型与 Auto（不做自动路由）
--------------------------------------------------------------------------------

  设计原则：系统不做任何按问题难度或类型的自动路由——不评估问题
  复杂度、不推荐模型、不替用户做选择；用户选择了哪个模型，就用
  哪个模型。

  Auto 选项的语义：
  - Auto 表示"跟随全局默认模型"：用户在设置页自行配置默认模型
    （初始建议选择一个性价比高的基础模型，如 qwen-turbo 或
    deepseek-chat，覆盖多数日常咨询），选 Auto 的请求统一使用该
    默认值。
  - Auto 不是智能路由：不读取问题内容、不做复杂度打分、不按场景
    切换模型；它在任何情况下都固定使用全局默认模型，行为完全
    可预期、可解释。
  - 用户可随时在发送框旁的选择器中把 Auto 改为具体模型，选择对该
    会话生效，也可在设置页修改全局默认。

  与意图路由的关系（不冲突）：
  - 寒暄、通用非法律问题仍由意图路由判定后走低成本直答（不注入
    RAG、不核验），这是"是否走完整法律流水线"的判定，属于意图
    路由职责，与"用哪个模型"的模型选择互不影响、互不耦合。

  达到的效果：模型选择逻辑全链路透明——答辩可以明确表述"我们不
  做黑盒路由，选哪个模型、是否用本地隐私引擎，完全由用户决定"，
  演示时也可现场演示 Auto 与四个具体模型之间的随意切换。

--------------------------------------------------------------------------------
8.4  任务调度器（任务编排式多智能体 · 已实施）
--------------------------------------------------------------------------------

  现状：意图路由只分法律/寒暄/通用三类，所有法律问题都走同一条
  通用问答模板。

  具体做法：把意图路由升级为"任务调度器"（src/agents/task_scheduler.py），
  在意图判定之后把法律问题细分为三类任务，分派到对应的专业处理
  管线（主管-专家形态，内部完全复用现有模块）：
  - 法律问答管线：标准流程——查询重写 → RAG 检索 → 生成 → 引用核验
    → 六维评分（与现状一致）；管线向模型开放工具调用（见 8.5），
    模型认为"一次检索不够"才调用，不调用时行为与现状完全一致；
  - 合同审查管线：文档解析优先（解析用户上传的合同/文书），使用
    合同审查专用提示词，输出结构化风险清单（条款类型 / 风险点 /
    法律依据 / 修改建议）；核验升级为"文档引文核验"——回答中引用
    文档原文的句子与上传文档逐字比对，防止模型编造合同条款；
  - 时效查询管线：提问含废止关系法律名（婚姻法、合同法、担保法等，
    法律名清单动态取自本地注册表，不硬编码）且含"有效/废止/失效"
    类词时，直查法律时效注册表，结论核心事实（废止日期、替代法律）
    完全由注册表给出，模型只负责组织语言与补充实务提示，回答标注
    "来源：法律时效注册表"，不检索不核验，秒级出结论。
  任务分类使用确定性规则（关键词正则 + 注册表数据）完成，不用大
  模型判断；规则不命中一律落回法律问答管线（回退安全，最坏情况
  等于现状，不退化）。
  复杂推理不单设管线：多事实 + 多法条竞合场景由 8.5 的工具调用
  覆盖（模型自主决定是否多次检索），避免重复建设。

  达到的效果：合同审查不再套用通用法律问答模板，输出专业结构化的
  风险清单且文档引用可逐字核验；时效问题零 RAG 零核验、直查注册表
  秒级出结论；可画出"任务分派流程图"，用实际案例对比各管线的输出
  差异。

--------------------------------------------------------------------------------
8.5  工具调用式智能体（务实版 · 已实施）
--------------------------------------------------------------------------------

  目标：让模型具备"自主决定调用什么工具、按什么顺序"的能力
  （ReAct：思考 → 行动 → 观察 → 得出结论），这是多智能体最直观
  的形态。本实现收敛为务实版：2 个工具 + 循环上限 3 轮，成本与
  风险可控。

  具体做法：
  - 为模型开放两个法律工具（src/agents/tools.py）：检索法条（参数：
    检索词，可指定法律名称）与查询法律时效（参数：法律名称）；
    工具执行只触碰本地向量库与本地注册表，无任何外部调用；
  - API 引擎使用百炼的原生函数调用能力（function calling）实现
    工具调度（src/llm/base.py 定义工具契约，api_client 实现
    complete_with_tools / complete_stream_with_tools）；工具循环
    引擎（src/agents/agent_loop.py）控制轮次，上限 3 轮，每轮工具
    决策的 token 上限约 512，防死循环、防费用爆炸；
  - 离线引擎的 7B 模型工具调用能力有限，不启用函数调用，自动降级
    为提示词注入模式（"检索结果已由 RAG 提供，直接基于参考块回答"），
    保证离线引擎仍可用，前端无感知变化；
  - 出错降级：工具循环任何一步异常（网络错误、参数错误、本地引擎
    不支持）自动退回普通生成路径（等于现状），绝不返回空白或半截
    回答；失败的步骤仍记录进工具轨迹，可查可讲；
  - 工具结果只作模型参考，不直接进入回答；最终回答的引用仍以引用
    核验为准——工具检索到的法条并入核验视野一起核验，可信闭环不
    放松；
  - 流式传输：工具循环阶段通过新增的 SSE agent_status 事件推送每
    步状态（运行中 / 完成 / 失败，含工具名与结果摘要），最终回答
    照常逐字流式输出；非流式接口同步执行，轨迹随响应返回；
  - 前端展示：生成中回答上方显示工具状态行（正在检索… → 命中 N
    条），回答详情面板新增可展开的"工具调用轨迹"区块，展示每一
    步的工具名、参数、结果摘要与耗时，作为答辩亮点；
  - 安全约束：工具参数清洗（长度上限、控制字符剔除）；输入守卫
    仍在调度之前最先执行。

  达到的效果：回答"需要多部法律交叉验证"类问题时，系统自动按需
  多次检索而非一次 Top-K；Agent 感最强、答辩展示度最高；同时成本
  与风险可控（工具收敛、循环封顶、出错必降级）。

--------------------------------------------------------------------------------
A.1  三种部署形态对比
--------------------------------------------------------------------------------

形态一：云端服务器部署本地模型（服务端本地引擎）
──────────────────────────────────────────────
  架构：用户浏览器 → 云服务器（带 GPU）→ 本地 Qwen 模型，数据只到
       服务器、不发给任何外部 API。
  优点：数据不流出服务端；隐私叙事强；模型统一管理。
  缺点：需要 GPU 云服务器（约 1-2 元/小时）；多人并发时显存可能
       不足（7B fp16 约 14GB）。
  适用：对"数据不出服务器"有要求的演示场景。

形态二：用户本机部署模型
──────────────────────
  架构：用户电脑 → 本地 Qwen 模型，仅本机推理，数据完全不出本机。
  优点：最强隐私保护；无 API 费用。
  缺点：用户需要 GPU（至少 16GB 显存）与 14GB 模型下载；环境配置
       复杂（CUDA/cuDNN/PyTorch 版本兼容）；无法控制用户端模型版本。
  适用：个人长期使用、数据高度敏感场景、非竞赛环境。

形态三：纯 API 方案
─────────────────
  架构：用户浏览器 → 轻量服务器 → 千问/DeepSeek 等 API。
  优点：零部署复杂度、不需要 GPU、模型能力最强。
  缺点：所有请求产生 API 费用；依赖外部服务可用性；数据发送给第三
       方（需脱敏与知情同意机制）。
  适用：快速原型、无 GPU 环境、预算充足。

--------------------------------------------------------------------------------
A.2  本项目推荐：双引擎共存，API 为默认、本地为可选隐私引擎
--------------------------------------------------------------------------------

  决策要点：
  1. 体验优先：默认走 API，打开浏览器即用，无 GPU 门槛；
  2. 隐私可选：GPU 与模型就绪时开放"离线调用"，用户按需选择——
     敏感问题数据不出本机；系统检测到 PII 时主动建议切换；
  3. 模型自主：API 端接入千问三档与 DeepSeek，选择权完全交给用户
     （Auto 仅跟随用户自己设置的全局默认，不做任何自动路由）；
  4. 可信不变：无论哪个引擎/模型，都走同一套引用核验与六维评分闭环；
  5. 可展示性：模型使用分布、成本曲线、隐私模式使用情况均可现场
     演示，且"不做黑盒路由"本身就是清晰的答辩叙事。

  硬件要求（仅本地引擎需要）：
  - GPU：至少 16GB 显存（推荐 RTX A4000 / RTX 3080 / RTX 4070）；
  - 内存：至少 16GB；磁盘：至少 50GB（模型 14GB + 向量库 + 数据）。
  说明：本地引擎未就绪时，服务照常以纯 API 模式运行，不做强制要求。

  推荐云平台（如需租用 GPU 演示本地引擎）：
  - AutoDL（https://www.autodl.com/）：按量计费，A4000 约 0.88 元/小时；
  - 阿里云 GPU 云服务器：T4 16GB 规格；
  - 矩池云（https://www.matpool.com/）：学生优惠。

  - 前端在回答旁标注实际使用的模型名；选择"离线调用"时明确提示
    "数据不出本机"；
  - 用户对"哪些问题走云端、哪些走本地"拥有完全决定权。

B.4  常见问题
--------------------------------------------------------------------------------

  Q: 页面打不开，显示"无法连接"？
  A: 可能是服务端电脑关机或内网穿透断开了，请联系服务端管理员确认。

  Q: 回答很慢？
  A: 法律类问题需要检索法条 + 大模型推理，通常需要 15-60 秒；本地
     引擎模式会更慢（7B 模型本地推理）。超过 2 分钟无响应请刷新重试。

  Q: 回答内容不准确？
  A: 点击右侧"引用核验"页签查看法条引用是否准确；发现错误可用
     👍👎 反馈。

  Q: 支持哪些文件格式上传？
  A: 支持 txt、md、docx、pdf、jpg/png/bmp 等；单文件不超过 10MB，
     最多 5 个附件。

  Q: 我换了浏览器，之前的会话还在吗？
  A: 同一账号登录后，会话和收藏会自动从服务端同步恢复。

  Q: 选离线调用提问，数据和之前有什么不同？
  A: 离线调用下你的问题与上传文档只在本机处理，不发送给任何外部
     服务；回答质量可能略低于云端大模型，适合隐私敏感场景。

                        实 施 建 议（更新版）
================================================================================

作为新手，建议按以下优先级和时间安排推进（9 阶段版本，8 周）：

  第1周：阶段一（流式输出加固）
     → 让流式效果流畅可靠，演示不翻车

  第2周：阶段二（问答缓存层） + 阶段三（服务端会话管理）
     → 性能与安全双提升，是与同类项目拉开差距的关键

  第3周：阶段七（数据工程）
     → 扩充法律数据，构建评测数据集

  第4周：阶段四（效果对比框架）
     → 跑出对比数据，形成量化报告

  第5周：阶段五（LangSmith） + 阶段六（多用户并发）
     → 工程化完善

  第6周：阶段九（一键部署与团队测试）
     → 让团队成员开始测试，收集反馈

  第7-8周：阶段八（模型层与智能体架构升级）——答辩核心亮点
     → 先做主线（抽象层 + 离线/API 两级选择 + 隐私模式 + 默认模型
       与 Auto，约 3-4 天）
     → 再做任务编排式多智能体（约 3-4 天）
     → 时间充裕最后做工具调用式智能体（约 4-5 天，可选）
     → 知识图谱已不再列为单独实施项，如对知识图谱感兴趣可在数据
       工程阶段为法律数据补充"法条关联关系"（如引用关系、废止
       关系），作为 RAG 之外的可选增强

  核心原则：
    - 缓存（阶段二）与会话管理（阶段三）最容易被忽视但最能体现
      实战工程能力，评委非常看重这类"非功能需求"
    - 一键部署（阶段九）让项目具备"可复现性"，是评审加分项
    - 阶段八是答辩亮点，但不必追求全部做完——主线（模型层 + 用户
      可控 + 隐私模式）稳定落地，配上模型使用统计与演示数据，效果
      就已足够出彩
    - 不要追求全部阶段做完——哪怕只做到阶段四，只要数据扎实、演示
      流畅，也比全做但每样都半成品好得多
