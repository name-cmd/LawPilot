法信通 LawTrust — 技术效果对比评测方案 + 数据工程完善方案
（2026-08-11 调研分析版）
========================================================================

本文档回答两个问题：
  问题一：项目中的 RAG / Agent / 三级引用核验 / 六维可信评估等技术，
          如何体现出"AI 推理（Inference）"的效果与指标？具体怎么对比、
          从哪些方面对比、能得到哪些直观（可视化）的对比数据？
  问题二：当前数据工程（只有 6 部法律、1950 条法条的嵌入库）不完善、
          不系统，如何通过完善数据处理来全面提升模型在法律场景的
          处理能力？

写作原则：先讲"它是什么、为什么需要"，再讲"怎么实现"，每项改进
都给出落地的文件、脚本、验收标准，方便按步骤执行。

========================================================================
第一部分  如何体现与对比 AI 推理效果（问题一）
========================================================================

----------------------------------------------------------------------
1.1 先搞清楚：什么是"AI 推理效果"，本项目哪些环节算"推理"
----------------------------------------------------------------------

通俗类比：模型就像一位刚毕业的见习律师。你问他问题，他要经历
"查资料（检索）→ 组织回答（生成）→ 核对法条（核验）→ 自我打分
（可信评估）"。这整条流水线（pipeline）里的每一次计算，都是
"Inference（推理）"。用户通常以为只有"生成回答"那一步是推理，
其实检索、核验、评分每一步都是模型/算法的推理，且互相影响。

本项目现有推理环节及其"可被量化的效果"盘点：

  1) RAG 检索（src/knowledge_base + src/pipeline 的多查询检索）
     —— 效果体现：能否检索到"正确的那条法条"。
     可量化：top-k 命中率、相关度分数、跨查询去重质量。

  2) LLM 生成（src/llm，百炼 7 模型 / 本地 Qwen2.5-7B）
     —— 效果体现：回答是否准确、完整、格式是否符合法律三段式。
     可量化：参考答案匹配率、引用条号正确率、语义忠实度（faithfulness）。

  3) Agent 工具循环（src/agents：search_articles / check_law_validity）
     —— 效果体现：模型是否会主动用工具、用对工具、不再答非所问。
     可量化：工具调用次数、工具成功率、决策轮数、对比"不用工具时
     的答对率提升幅度"。

  4) 三级引用核验（src/citation_verifier）
     —— 效果体现：引用"逐条验真"的能力（防幻觉的最后防线）。
     可量化：overall_citation_score、内容吻合分、条号不符检出率。

  5) 六维可信评分（src/trust_eval）
     —— 效果体现：把"质量"压缩成 0~100 分 + 六维雷达，供人一眼看懂。
     可量化：overall_score、各维度分、弱维度清单。

  6) 自一致性评估（src/uncertainty）
     —— 效果体现：同一问题多次采样，回答是否前后一致（不确定度）。
     可量化：avg_consistency（N×N 相似度均值）、不确定性分级。

  7) 输入守卫（src/guardrails）+ 意图路由（src/pipeline/intent_router）
     —— 效果体现：滥用请求是否被拦、寒暄是否走轻量路径（省成本）。
     可量化：拒答准确率、路由准确率。

一句话总结现状：功能都有了，但"证明它们有效"的评测体系还很薄
（详见 1.2），这正是第一部分要解决的。

----------------------------------------------------------------------
1.2 现有评测的四个不足（先认清问题，方案才有针对性）
----------------------------------------------------------------------

  不足 1：测试集太小、且与知识库脱节。
    data/benchmark/legal_qa_gold.json 只有 10 题；
    其中 qa003（刑法）、qa004（道路交通安全法）、qa005（消费者权益
    保护法）、qa006（公司法）引用的法律【根本不在知识库里】！
    也就是说这 4 题靠"模型自身知识"回答，RAG 检索不到正确法条，
    gold_citation_recall 即使命中也是碰运气，无法证明 RAG 的价值。

  不足 2：指标过于粗糙。
    当前核心指标 gold_citation_recall 只是"字符串包含"判断
    （run_legal_trust_benchmark.py 的 _citation_hit，把"第"和"条"
    去掉后做子串匹配）。模型回答"第三十七条"写成"第37条"或
    "37条"就可能漏判/误判；也无法回答"检索到了但没引用"这类问题。

  不足 3：没有"检索质量"的评测。
    RAG 系统的好坏首先要看"检索那一环"（法条是否被搜出来），
    当前没有任何 Recall@k / MRR 等指标，检索烂了也发现不了。

  不足 4：没有多模型横向对比、没有成本与延迟口径。
    注册表有 7 个模型，但没有脚本在同一批题目上对比它们的
    准确率/信任分/延迟/token 成本；API_LOG_USAGE 的 token 用量
    只打印不落盘。

1.3 指标体系设计：从哪些方面对比（共 5 组指标）
----------------------------------------------------------------------

以下指标分 5 组，全部可以在现有数据/代码基础上计算出来。
括号内给出计算公式或出处，标注"可直接算"的是现有代码已输出、
无需新开发。

【A 组：检索质量指标】（判断"查资料"查得准不准）
  A1. Top-k 命中率（Hit Rate@k）
      定义：gold_article 是否出现在检索结果前 k 条中。
      公式：命中题数 ÷ 总题数，分别取 k=1,3,5。
      数据来源：pipeline 输出的 retrieved_articles（现有字段，直接可用）。
  A2. MRR（平均倒数排名）
      定义：正确法条在检索结果里的位次倒数，越靠前越高。
      公式：MRR = (1/rank₁ + 1/rank₂ + …) ÷ 题数；没搜到记 0。
  A3. 检索平均相关度
      定义：正确法条那条记录 relevance_score 的均值
      （现有 format_article_record 已输出 relevance_score）。
  A4. 无检索率：检索结果为空或全部低于 0.35 阈值的题数占比
      （反映知识库覆盖漏洞，qa003~006 这类题会暴露出来）。

【B 组：生成质量指标】（判断"组织回答"答得好不好）
  B1. 标准答案匹配率（Answer Match Rate）
      当前 gold 集带 answer 短答字段（如"三十日"），可用三类匹配：
      精确匹配 / 子串匹配 / 语义匹配（bge 余弦 ≥ 0.85 视为命中，
      本地模型即可算，不花 API 钱）。
  B2. 引用准确率（Citation Accuracy）
      用现有 citation_verification.overall_citation_score 直接取。
      同时统计"条号不符"（wrong_article_mismatch）题数占比——
      这是最能暴露幻觉的指标。
  B3. 忠实度 Faithfulness（RAGAS 风格，本地化实现）
      定义：回答中的每个论断是否被检索到的上下文支撑。
      落地：复用现有 L3 隐性论断核验（implicit_verifier.py 的
      Erlangshen-NLI），把回答分句 → 逐句与"检索到的法条原文"
      做 NLI 蕴涵判断 → 有支撑句数 ÷ 总论断句数。
      成本：NLI 是 330M 小模型，CPU 可跑，无需 API。
  B4. 检索使用率：use_rag=True 的题中"实际注入过检索块"的比例。

【C 组：可信与安全指标】（判断"核验与打分"是否真实有效）
  C1. 六维可信均分 + 雷达（现有 avg_radar，直接可用）。
  C2. 自一致性：avg_consistency 均值、低一致（<0.75）题数占比。
  C3. 安全准确率 Safety Accuracy（现有 legal_safety 集，直接可用）。
  C4. 时效判断准确率：对"已废止法律"提问，系统是否给出废止警告
      （现有 validity_warnings 字段）。

【D 组：性能与成本指标】（判断"快不快、贵不贵"）
  D1. 端到端延迟：首 token 延迟 + 总耗时（ms），分模式记录。
  D2. Token 消耗：输入/输出 token 数（需在 api_client 的
      usage 回调处落盘收集，小改造）。
  D3. 单题成本（元）：按注册表 price_tier 档位折算
      =（输入 token×输入价 + 输出 token×输出价）÷ 1000000。
  D4. 核验与重生成开销：重生成触发率（regeneration_attempts>0 占比）、
      自一致性 5 采样的额外耗时。

【E 组：对照组指标】（用于"对比"的锚点）
  E1. 无 RAG 基线（纯模型记忆回答）——no_rag 模式已支持。
  E2. 参考答案人工评分（可选）：10 题小样本请人按 1~5 分打分，
      作为"机器指标"的交叉验证。

1.4 对比实验设计：具体怎么对比（4 个矩阵）
----------------------------------------------------------------------

矩阵 1：系统消融对比（证明"每一环都值得做"）★ 最重要的对比
  同一批题 × 4 种模式跑一遍，纵向对比：
    no_rag    = 无检索、纯 LLM（裸模型，体现"模型原生能力"）
    rag       = 只开检索 + 生成（体现"RAG 的增量"）
    full      = 检索 + 核验 + 条件重生成（当前默认，体现"核验闭环"）
    agent     = full + 工具调用（体现"Agent 的增量"）
  产出：一张 4 行 × 15 列的表（A~E 组指标各一行维度），
  以及"逐题明细"（同一道题 4 种模式的回答差异）。
  预期结论示例："qa001 在 no_rag 下答对但引用错误 → full 模式下
  通过重生成修正"，这类案例就是比赛答辩时的最佳素材。
  说明：脚本已支持 --mode，本方案只做"结果收集 + 报告生成"。

矩阵 2：多模型横向对比（7 模型选型依据）
  同一批题 × 7 个 API 模型（qwen3.7-plus/turbo/max、deepseek-v4-
  flash/pro、kimi-k2.6、glm-5.2），各跑 full 模式：
  产出：模型×指标的得分矩阵 + 成本-效果散点图（横轴=单题成本，
  纵轴=综合得分）→ 一眼选出"性价比最优模型"。
  需要小改造：run_legal_trust_benchmark.py 增加 --model 参数
  （QwenModel 构造时指定 model_id，已有透传链路，改动很小）。

矩阵 3：超参对比（检索与重生成）
  TOP_K_RETRIEVAL ∈ {3, 5, 8}、RETRIEVAL_MIN_RELEVANCE ∈
  {0.25, 0.35, 0.45} 各跑一遍，看 A 组指标的变化 →
  为 Config 选默认值提供数据依据（现有默认 0.35/5 是拍脑袋定的）。

矩阵 4：鲁棒性对比（一致性）
  同一题 × N_SAMPLES ∈ {1, 2, 5}（温度 0.3~1.1），对比
  回答质量与 avg_consistency 的关系 → 证明"自一致性作为
  质量代理指标"的可靠性。

      多少？哪个模型性价比最高？"三个问题。

第二部分  数据工程完善方案（问题二）
========================================================================

----------------------------------------------------------------------
2.1 现状盘点与核心问题（先认清差距）
----------------------------------------------------------------------

当前现状（已核实）：
  · 知识库仅 6 部法律、1950 条法条（民法典 1260 / 民诉法 291 / 宪法
    143 / 劳动法 107 / 劳动合同法 98 / 婚姻法 51）。
  · 已废止的婚姻法仍在库中（靠 status 字段标记，检索时过滤）。
  · 分块策略：1 条法条 = 1 个 Document（law_chunker.py），无超长
    条文切分；实测 1950 条中 3 条超 500 字（宪法，最长 1008 字，
    bge-base-zh 窗口 512 token ≈ 700~800 汉字，超长即被截断丢字）。
  · law_name_resolver 的 KNOWN_LAWS 只有 4 部法律（陈旧，与实际
    6 部不一致）。
  · law_repeals.json 有瑕疵数据（"民事诉讼法-checkpoint"，来自
    data/raw/.ipynb_checkpoints 下的残留文件）。
  · 无司法解释、无行政法规/规章、无判例 —— 而真实法律咨询中
    "司法解释 + 裁审规则"才是高频依据（如劳动争议、婚姻财产分割）。

由此导致的"模型表现差"的因果链（数据 → 推理效果的传导）：
  数据缺法 → 检索 Hit@k 低 → 注入错误/空上下文 → 生成靠模型记忆
  → 引用核验失败 → 重生成兜底 → 信任分低 + 延迟成本上升。
  只要把数据层补好，A~D 组指标会同步改善，这就是第二部分能
  "全面提升处理能力"的机理。

2.2 法律数据金字塔规划（要覆盖什么，按优先级）
----------------------------------------------------------------------

按照"法律效力层级 + 咨询频次"设计入库优先级（P0 最高）：

  P0 核心实体法（当前缺的最关键）：
    刑法、公司法、消费者权益保护法、道路交通安全法
    （这 4 部正是现有测试集引用了但库里没有的！先补这 4 部，
    马上让 qa003~qa006 变得可测。）
  P0 高频配套法规：
    工伤保险条例、劳动合同法实施条例、社会保险法、
    劳动争议调解仲裁法、劳动合同法司法解释（一）（二）、
    民事诉讼法解释（大量诉讼问题靠它）。
  P1 常用民商事法律：
    行政处罚法、行政许可法、行政复议法、行政诉讼法、
    产品质量法、食品安全法、旅游法、广告法、
    著作权法、商标法、专利法、民法典婚姻家庭编解释（一）（二）、
    民法典合同编通则解释。
  P1 刑事与程序：
    刑事诉讼法、刑法修正案配套司法解释、反电信网络诈骗法。
  P2 扩展（可选，用于覆盖面宣传）：
    未成年人保护法、妇女权益保障法、老年人权益保障法、
    反家庭暴力法、继承编解释、民法典物权编解释。
  P3 判例类（进阶，量力而行）：
    最高人民法院指导性案例（目前已发布 40+ 批，每批 3~6 例）、
    公报案例。建议先不做全文，只做"裁判要旨"摘要块（每题一句，
    检索友好的短块），用于演示"类案检索"能力。

数据来源（全部公开免费，无需授权）：
  · 国家法律法规数据库 https://flk.npc.gov.cn （官方权威，
    法律/行政法规/司法解释均有，支持 PDF 下载）
  · 最高人民法院官网 www.court.gov.cn （司法解释、指导案例）
  · 国务院政策文件库 www.gov.cn/zhengce （行政法规、部门规章）
  · 百度百科/维基仅作交叉核对，不作为主来源。

2.3 数据处理流水线设计（全流程，每步都有产出物）
----------------------------------------------------------------------

  第 1 步：获取（scripts/fetch_laws.py 新增）
    · 从官方库按"效力级别=法律"逐部下载 PDF/HTML 到
      data/raw/，命名统一为《法律全称.md》（去掉"中华人民共和国"
      前缀，保持与 law_name_resolver 剥离逻辑一致）。
    · 每部法律登记一行元数据（data/law_registry.json 扩展）：
      {name, source, issue_org, issue_date, effective_date,
       amend_history[], status, category, has_interpretation}
      —— 让"时效查询"功能可以回答"现行版本、谁颁布的、改过几次"。

  第 2 步：清洗与结构化（升级 md_converter.py）
    · 增加清洗规则：
      a. 剔除目录、页码、"（2021年修正）"这类排版噪声；
      b. 修正错别字与全半角（"第l条"→"第1条"、"（一）"统一半角）；
      c. 删除 data/raw/.ipynb_checkpoints 残留目录（一次性清理，
         避免再次污染 law_repeals.json）；
      d. 条文标题补全：只写"第一条 总则"的行拆成"第1条" + 标题；
      e. 法律名规范化：文件名去掉前缀后仍要保留原名全称字段
         （law_name 与 full_name 分开存）。
    · 输出校验：转换后自检"条文号是否连续、是否有重复"，
      与官方目录比对条文总数（防漏页）。

  第 3 步：增强元数据（law_parser.py 扩展）
    每条法条 metadata 增加：
      · category 细化：从 8 大类细化到 40+ 小类（如 劳动→
        {劳动合同/工伤保险/工资工时/劳动仲裁/社保}），供检索
        过滤与前端"按领域浏览"；
      · cross_refs：条文间"依照第X条规定"的内链（正则抽取），
        为后续"法条图谱"打基础；
      · 引用标签：该条是否被其他法律引用（民法典第1260条列出
        9 部废止法，反向建"废止链"）。
    同步修复 law_name_resolver：KNOWN_LAWS 改为"启动时从向量库
    metadata 动态构建 + 内置别名表（民诉法→民事诉讼法、劳动仲裁法
    →劳动争议调解仲裁法、刑法修正案→刑法 等）"，不再硬编码 4 部。

  第 4 步：分块策略升级（law_chunker.py 重写）★ 技术重点
    现状问题：1 条法条 1 块，超长被截断；且丢失"款/项"定位能力。
    新策略（父子分块，参照当前 citation_verifier 已按款/项切分的
    能力设计，二者对齐）：
      · 父块：完整条文（保留全文，供引用核验逐字比对）；
      · 子块：超长条文（>300 字）按 款（第X款）/ 项（（X））切分，
        子块 metadata 带 parent_article_num，检索命中的子块可
        通过父块恢复完整条文注入上下文；
      · 块间引用锚点：子块开头保留【第X条第X款】头行，
        保证引用核验的 quoted_text 能精确定位；
      · 章首导语块（可选增强）：每章开头生成一条"章摘要"
        （本章共 N 条、涵盖 主题词列表），提升"跨多条的综合问题"
        的召回（如"劳动合同解除有哪些情形"）。
    验证方式：转换后统计"超 512 token 块占比 = 0"；用
    retrieval_gold.json 对比新旧分块的 Hit@5。

  第 5 步：质检与版本管理（新增 scripts/qa_data.py）
    · 一致性检查：向量库条数 == processed JSON 条数；每条
      metadata.status 与 law_registry 一致；无重名法律；
    · 样本抽查：每部法律抽 5 条人工核对正文无乱码/截断；
    · 版本管理：data/processed 下每部法律 JSON 内记录
      source_sha256 + fetched_at；法律修正后重新入库时保留
      "上一版本"标记（law_version 字段已存在），保证时效判断
      有据可查；
    · 构建流水线脚本化：convert → qa → build_knowledge_base
      一键跑通（新增 scripts/rebuild_all.py），防止手工漏步。

  第 6 步：评测数据联动（与第二部分闭环）
    · 每新入库一部法律，配套补充 5~10 条 QA 进 benchmark
      （生成方式：先由模型生成，再人工核对 gold 答案），
      保证"数据量 ↑ → 评测集 ↑ → 效果可验证"同步增长。

----------------------------------------------------------------------
2.4 司法解释与判例的特别处理（法律问答的"胜负手"）
----------------------------------------------------------------------

  为什么重要：现实问题几乎都是"法条 + 司法解释"组合适用。
  例：问"单位欠薪，我能否直接解除合同并要经济补偿？"
      答：劳动合同法第38条（劳动者可解除）+ 第46条（应支付补偿）
      + 劳动合同法司法解释（一）第45条（未支付劳动报酬的界定）。
  只有法条没有解释，回答会"对一半"。

  处理方案：
  · 司法解释按《最高人民法院关于适用〈XX法〉的解释（一）》
    独立入库，law_name 保留全称；metadata 加
    {interpretation_of: 母法名, doc_type: "judicial_interpretation"}；
  · 检索排序：向量距离相同时，法律优先于解释（retrieval_utils
    排序 key 加分项，代码 5 行）；
  · 指导性案例：只入"裁判要旨"段（100~200 字），每条 metadata
    加 {case_no, court, year, topic}；演示时用"参考类似判例"
    话术回答，不承诺个案结果（与 safety 规则兼容）。

----------------------------------------------------------------------
2.5 数据工作如何量化回馈到模型效果（闭环验证表）
----------------------------------------------------------------------

每完成一个 P0/P1 批次，跑一次第一部分的全量评测（no_rag/full/
agent 三模式），记录以下"数据 → 效果"联动指标：

  · 检索命中率：新增法律后，对应类别的 Hit@5 从 ~0 升到 ≥0.8；
  · 引用准确率：overall_citation_score 均值提升目标 ≥0.1；
  · 六维信任分：truthfulness 维度（引用准确率占 0.6 权重）
    提升目标 ≥5 分；
  · 覆盖率：法律名解析成功率（law_name_resolver 能识别的新入库
    法律名）提升到 100%；
  · 质检通过率：入库数据 100% 通过第 5 步自检。

----------------------------------------------------------------------
2.6 分阶段实施计划（问题二的执行路线）
----------------------------------------------------------------------

  阶段 D1「先补齐、快速见效」（约 1~2 天）
    · 入库 4 部 P0 法律（刑法/公司法/消保法/道交法）——直接用
      现有 convert + build 脚本跑通，检验流水线对"新数据"的
      兼容性（大概率要修 law_name_resolver 与转换容错）；
    · 清理 ipynb_checkpoints 残留与 law_repeals 瑕疵；
    · 扩充 legal_qa_gold 至 30 题并加入 retrieval_gold.json；
    · 跑矩阵 1，验证 qa003~006 的 A 组指标恢复。
    验收：4 部新法检索 Hit@5 ≥ 0.8；报告页能对比新旧报告。

  阶段 D2「系统性增强」（约 3~5 天）
    · 完成 2.3 的第 2~5 步（清洗规则 / 元数据增强 / 父子分块 /
      质检脚本 / rebuild_all.py）；
    · 入库 P0 配套法规（工伤保险条例、司法解释等 6~8 部）；
    · law_name_resolver 动态化 + 别名表。
    验收：全部法律通过质检；超 512 token 块占比为 0；
        检索 gold 的 Hit@5 在 30 题上 ≥ 0.85。

  阶段 D3「扩展与沉淀」（视时间量力而行）
    · P1 民商法与程序法批量入库（10~15 部）；
    · 指导性案例"裁判要旨"入库（可选）；
    · 建立"数据周更"意识：每次演示前跑 rebuild_all + 质检。
    验收：知识库覆盖 8 大咨询类别的 80% 高频问题。

========================================================================
第三部分  总路线图与汇报口径
========================================================================

  两部分的耦合关系（务必向评委讲清）：
    第一部分（评测体系）= 体温计 —— 证明"系统每一环都有用、值得信"；
    第二部分（数据工程）= 补身体 —— 让"知识覆盖从 6 部法律到 30+ 部，
    检索命中从碰运气到稳定命中"。
    二者互为因果：没有数据，评测暴露不出问题；没有评测，数据改进
    无法证明价值。

  建议汇报主线（10 分钟版）：
    1. 开场：一条真实法律问题，现场演示全链路（检索→生成→核验
       →六维评分），切到核验结果页展示逐条比对；
    2. 对比：同一问题 no_rag vs full 的消融图（图 2）——"没有
       RAG 时它编造法条，有了核验闭环它自纠"；
    3. 选型：成本-效果散点图（图 3）——"7 模型同题对比，我们
       用数据选择了性价比模型"；
    4. 数据：展示知识库从 6 部到 30+ 部的增长曲线 + Hit@5 提升
       折线——"效果提升来自系统化数据工程"；
    5. 收尾：评测报告页（图 1~6 全景）作为可复现证据。

  风险与注意点：
    · API 评测有费用：7 模型 × 30 题 ≈ 每轮几元~几十元（max 档
      贵），控制批量与次数；mock 模式可免费先跑通脚本；
    · 数据版权：仅用官方免费公开的法律文本，不引入付费库；
    · 别贪多：以"能跑出对比报告"为准，P2/P3 数据量力而行，
      避免花了时间却上不了演示。
